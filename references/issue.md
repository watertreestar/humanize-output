# Issue、任务与需求

一条合格的 Issue 应让接手者理解问题、确定范围、实施改动并验证完成，而不必反向猜测发起人的真实意图。

## 审查要点

- 先写观察到的问题或期望结果，不要默认从空泛的“背景”开始。
- 区分已知事实、原因假设和建议方案，避免把猜测写成结论。
- 在已有信息中补充相关环境、复现步骤、示例、日志、链接和影响对象；缺失时列为待确认，不要编造。
- 明确会改变实现方式的范围边界和依赖。
- 验收条件应可以观察或验证。“优化”“支持”“提升”“用户友好”需要落到具体行为。
- 不要虚构优先级、工期、指标、负责人、错误原因或技术限制。
- 不要保留没有内容的仪式性章节。一个小缺陷可能只需要五行，不需要完整 PRD 模板。

## 可选结构

根据任务选择需要的字段：问题或结果、上下文、复现步骤或业务场景、范围、验收条件、验证说明、待确认问题。

验收条件优先描述外部可见行为。除非实现方案已经确定，否则不要把具体实现方式混入需求本身。

需要参考不同 Issue 类型的完整改写时，读取 `examples/issue-before-after.md`。其中包含缺陷、功能需求、性能、技术债、线上事故跟进和信息不足六类案例；使用其判断方法，不要复制示例中的数字和字段。
