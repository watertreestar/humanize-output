# 代码与实现产物

代码首先要适合当前仓库，在目标环境中能运行，并且后续维护者能够理解。看起来整洁不等于工程质量可靠。

## 审查要点

- 引入新写法前，先了解仓库现有约定、依赖、语言和运行时版本、架构边界及测试方式。
- 用最小但完整的改动解决当前问题，避免顺手重构无关区域。
- 没有现实需求时，不增加接口、基类、Factory、通用 Helper、配置层或包装对象。
- 命名要表达业务行为；注释应解释约束、原因和反直觉决策，不要复述代码语法。
- 按任务风险处理无效输入、缺少配置、权限失败、超时、上游错误和边界情况，不要只写理想路径。
- 不要编造 API、软件包、方法、参数、Schema 或平台能力；不确定时先验证或明确标注。
- 删除密钥、伪装成正式数据的示例值、提示词残留、无用脚手架和未处理的占位符。
- 增加或更新有针对性的测试，并如实说明实际执行过哪些验证。

## 设计模式与抽象

只有当某个模式能让已经存在的变化、生命周期、所有权边界或测试接缝更清楚时才使用它。代码“将来可能有多个实现”本身不足以证明现在需要抽象。
