# 改写前后示例

这些示例用于展示判断过程，不是要求所有产物照抄的模板。示例中的数据用于说明“有证据时如何写”；实际任务没有提供的数据必须标为待确认，不能自行补造。

| 类型 | 示例重点 |
|---|---|
| Issue / 任务 | 从抽象目标变成可执行、可验收的工作 |
| 架构 / ADR | 用事实、取舍和验证代替架构名词堆叠 |
| UI/UX | 让布局和组件服从真实业务流程 |
| 文档 / README | 让读者尽快完成正确操作 |
| 代码 / 注释 | 删除无依据的抽象，处理真实失败路径 |
| PPT / 项目汇报 | 用可核验结果和决策代替成果包装 |
| 日常对话 | 先解决问题，不用套话拉长回答 |

## 1. GitLab Issue

### 改写前

> **优化登录体验**
>
> 为了进一步赋能用户并全面提升系统可用性，需要对登录模块进行优化，打造无缝、高效、安全的使用体验。
>
> - 优化性能
> - 完善异常处理
> - 提升用户体验

### 改写后

> **SSO 回调超时后提供可恢复的错误提示**
>
> 生产环境中，身份提供方在 10 秒内没有响应时，`/auth/callback` 会一直停留在加载状态。页面没有重试入口，用户通常只能手动刷新。
>
> **范围：** 本次只处理回调超时；身份提供方配置调整不在范围内。
>
> **验收条件：**
> - 10 秒内没有收到响应时，用“登录超时，请重试”替换加载动画。
> - 点击“重试”会发起新的 SSO 请求；请求进行期间不能重复点击。
> - 重试成功后仍跳转到用户最初访问的地址。
> - 增加覆盖超时、重试和成功跳转的测试。

为什么更好：它把抽象的“提升体验”改成了已观察到的故障，限定了范围，并把完成条件写成可验证行为。这里的 10 秒属于示例已有上下文；如果原始材料没有给出超时时间，应写成待确认，不能在改写时发明。

更多缺陷、功能需求、性能、技术债、事故跟进和信息不足示例见 `examples/issue-before-after.md`。

## 2. 架构决策

### 改写前

> 我们将引入微服务架构、事件驱动设计和统一抽象层。这套面向未来的方案将全面提升系统的扩展性、灵活性和可维护性，为业务快速增长保驾护航。

### 改写后

> **决策：** 发票创建继续保留在现有服务中；PDF 渲染改由现有任务队列后的异步 Worker 处理。
>
> **为什么现在要改：** PDF 渲染占 `/invoices` 请求耗时的 82%，并且偶尔超过网关 5 秒超时限制。发票校验和持久化目前没有独立部署的需要。
>
> **代价：** PDF 生成完成前，用户会看到“处理中”状态。API 需要提供任务状态，支持人员也需要能够重试失败任务。
>
> **验证：** 先向 10% 的租户开放。连续 7 天满足发票创建 p95 低于 800 毫秒、渲染任务失败率低于 0.5% 后再继续放量；否则切回同步渲染。

为什么更好：每个架构变化都对应一个已观察到的约束，影响和代价被明确写出，放量条件也可以验证。实际 ADR 中的数字必须来自测量结果或经过确认的目标；如果没有数据，应说明需要先建立基线，而不是照抄示例数字。

## 3. UI 设计说明

### 改写前

> 设计一个现代化运营后台：顶部使用渐变标题，放置六张圆角统计卡片和彩色图标，加入流畅的悬浮动效，下方展示一张简洁表格。整体需要体现高级感和直观体验。

### 改写后

> **主要任务：** 运营人员查看失败付款，并批量重试符合条件的记录。
>
> 首屏以失败记录表格为主。表格上方持续显示失败原因、付款渠道、日期和重试资格筛选。每行展示付款编号、商户、金额、渠道、失败原因、上次尝试时间和重试状态。支持选择多行；执行批量重试前，先显示符合条件的记录数量。
>
> “今日失败”“可重试”“已阻止”使用紧凑的摘要条展示，不使用六张等权卡片。状态不能只靠颜色区分，需要同时提供文字和图标。设计稿覆盖加载、空数据、部分数据、无权限、重试中和批量处理结果。窄屏优先保留付款编号、金额、状态和行操作，次要字段进入详情页。

为什么更好：页面结构跟随实际操作流程和信息优先级，组件与状态来自业务需要，而不是来自流行的视觉样式。示例中的字段同样需要真实业务模型支持；如果任务没有提供字段，应把它们列为待确认项。

## 5. 代码、命名与注释

示例上下文：当前仓库只有 CSV 订单导入，已经提供 `parseOrderCsv`、`ImportError` 和数据库事务 API；暂时没有第二种导入格式。

### 改写前

```ts
// 通用处理器抽象，面向未来支持各种业务场景
interface IDataProcessor<T> {
  process(data: T): Promise<void>;
}

abstract class BaseProcessor<T> implements IDataProcessor<T> {
  abstract process(data: T): Promise<void>;
}

class CsvOrderProcessor extends BaseProcessor<string> {
  async process(data: string): Promise<void> {
    // 进行订单数据的处理
    await saveOrders(parseCsv(data));
  }
}

class ProcessorFactory {
  static create(type: string): IDataProcessor<unknown> {
    if (type === "csv-order") return new CsvOrderProcessor();
    throw new Error("unsupported");
  }
}
```

### 改写后

```ts
export async function importOrdersFromCsv(csv: string): Promise<void> {
  if (!csv.trim()) {
    throw new ImportError("订单 CSV 为空");
  }

  const orders = parseOrderCsv(csv);
  if (orders.length === 0) {
    throw new ImportError("CSV 中没有可导入的订单");
  }

  // 一批订单必须一起成功或失败，避免重试后留下部分重复数据。
  await db.transaction((tx) => tx.orders.insertMany(orders));
}
```

同时增加三个测试：正常导入、空文件、数据库写入失败时事务回滚。

为什么更好：当前只有一种导入流程时，接口、基类和 Factory 没有提供实际变化点，反而隐藏了核心行为。改写后的函数名表达业务目的，注释解释事务约束而不是复述语法，错误和验证也围绕真实失败路径。以后真的出现第二种导入流程时，再根据两者的共同变化决定是否抽象。

## 6. PPT / 项目汇报

示例上下文：以下时长、日期和队列等待数据均来自该项目的任务日志与运营记录。

### 改写前

> **项目成果**
>
> - 全面提升处理效率
> - 显著改善用户体验
> - 构建稳定可靠的技术底座

### 改写后

> **批处理改造把每日结算从 2 小时 10 分钟缩短到 38 分钟**
>
> - 统计范围：10 月 1 日至 10 月 28 日，共 20 个工作日
> - 口径：从运营点击“开始结算”到结果文件生成完成
> - 改造前中位数：2 小时 10 分钟；改造后中位数：38 分钟
> - 代价：高峰期队列等待时间增加 6 分钟，下一阶段需要拆分结算任务优先级
> - 本页数据来源：结算任务日志与运营值班记录

为什么更好：标题直接给出这一页需要听众记住的结论，指标有时间、口径和来源，同时没有隐藏代价。实际汇报不能套用这里的数字；没有测量数据时，应展示已完成的工作、验证方法和待补数据，而不是编造成果。

## 7. 日常对话与问答

### 改写前

> 用户：`npm install` 报 `EACCES`，怎么办？
>
> 助手：我理解你遇到这个问题一定很困扰。`EACCES` 是一个常见且至关重要的权限问题，可能由多种原因导致。以下是一些全面的解决方案：检查权限、清理缓存、重新安装、使用管理员权限，或者更换包管理器。总而言之，选择最适合你的方案即可。希望这些建议能帮助你顺利解决问题！

### 改写后

> 先不要用 `sudo npm install`，否则后续文件可能继续归 root 所有。
>
> 运行下面两条命令，把完整报错和输出贴出来：
>
> ```bash
> npm config get prefix
> npm install
> ```
>
> 如果报错路径在全局 npm 目录，优先用 nvm 安装并管理 Node，再重新安装依赖；如果路径在当前项目的 `node_modules`，需要检查该目录是不是以前用 `sudo` 创建的。你用的是 macOS、Linux 还是 Windows？不同系统的修复命令不一样。

为什么更好：回答先阻止一个常见但会扩大问题的操作，再用最少的诊断信息区分两类原因。它没有假装在缺少系统和路径信息时给出“全面方案”，也没有用安慰、总结和祝福稀释可执行步骤。
